# mini-code-agent：一个沙箱 coding agent 的评测报告

> 2026-11 · 代码：https://github.com/Aozak1Aok0/mini-code-agent
> 静态页：https://aozak1aok0.github.io/mini-code-agent/

## 1. 做了什么

一个能自己读代码、改文件、跑测试、失败后重试的 coding agent，以及一套用来判断它到底行不行的评测。

刻意不做通用编程助手：任务都是「一个带失败 `pytest` 的小仓库」，agent 在独立 workspace 里把测试跑绿。这样做的原因很直接——**解决率可以被脚本判定，不需要人来打分**。模型自述「我修好了」不算数，只有 `pytest` 退出码算数。

## 2. 架构

```
codeagent/
  loop.py         模型 → 工具调用 → 观察，循环到 finish 或步数上限
  tools.py        6 个工具：list_dir / read_file / grep / write_file / run_tests / finish
  sandbox.py      workspace 路径白名单 + 受限 pytest 子进程
  credentials.py  Windows 凭据管理器读 key（不落盘）
  run.py          CLI：复制任务 → 跑 agent → 落盘逐步 trace
```

工具集只有 6 个是刻意的：工具越多，模型选错的概率越高，评测就越难归因。`finish` 是显式终止信号，避免靠自然语言判断「它是不是做完了」。

### 沙箱边界

- 文件操作只能落在 workspace 根目录内，拒绝绝对路径与 `..`；
- 只允许跑 `pytest`，带超时；环境变量最小化；
- 工具层不提供网络。

这是 Windows 上可用的最小隔离。更强的隔离（Docker、只读挂载、nsjail）留在后续加固里——MVP 阶段先用能跑起来的方案。

## 3. 任务集（20 题）

| 类别 | 数量 | 例子 |
|---|---|---|
| bugfix | 10 | `mean([])` 除零、slug 连续分隔符、默认值 `None` vs `False` |
| feature | 4 | 时长解析 `1h30m15s`、重试装饰器、分页、CSV 导出 |
| refactor | 5 | 校验逻辑抽取、常量表、拆分模块、公共 API 约束、性能热点 |
| perf | 2 | 10 万行报表 7s → 1.5s 内；20 万事件 / 5 万用户 |

每个任务目录包含：

- `TASK.md`：需求或现象描述（0013–0015 只描述现象，不给文件名）；
- 可见测试：agent 能读能跑；
- `hidden/test_hidden.py`：复制 workspace 时被排除，可见测试通过后再跑一遍。

隐藏测试存在的理由不是「藏考点」，而是防止 agent 改测试拿分——脚本自己也会校验 `test_*.py` 的哈希。

## 4. 评测方法

1. 复制任务到 `runs/<suite>/<task>/workspace`（排除 `hidden/`）；
2. agent 循环，直到 `finish` 或步数上限；
3. 脚本自己跑 `pytest`，不信 agent 的自述；
4. 校验测试文件哈希，被改过直接判 `tests_modified`；
5. 可见测试通过后合并 `hidden/` 再跑一次，失败记 `hidden_test_failed`；
6. 记录步数、token、耗时与工具调用序列。

失败分类：`no_edit`（定位错）、`wrong_fix`（改错）、`no_test_run`（没跑测试）、`loop`（循环）、`tests_modified`、`error`。

## 5. 结果

单次全量（2026-11-06，`deepseek-chat`，20 题）：

| 指标 | 值 |
|---|---|
| 解决率 | 20 / 20（100%） |
| 平均步数 | 9.2 |
| token / 任务 | 12,372 in / 645 out |
| 延迟 P50 | 7.2s |
| 测试被改动 | 0 / 20 |
| 隐藏测试失败 | 0 / 20 |

分类：bugfix 10/10、feature 4/4、refactor 5/5、perf 2/2。

### 成本曲线

| 组 | 题数 | 平均步数 | 输入 token | P50 |
|---|---|---|---|---|
| 小题（0001–0018 中的单文件题） | 15 | 7.5 | 8,438 | 7.1s |
| 大题（0016–0020） | 5 | 14.2 | 24,172 | 13.0s |

大题输入 token 是小题的 **2.9 倍**，解决率不变。

## 6. 三次设计迭代

**第一轮（12 题）**：全部一次通过，平均 7.2 步。失败分类器拿不到样本，说明题目对当前模型太简单。

**第二轮（15 题，加 3 个隐式需求）**：只给现象不给文件名，要跨文件定位。步数 9.0 vs 7.5、输入 +21%，仍然 15/15。难度只抬高了成本。

**第三轮（20 题，加大题与信号实验）**：

- 0019 把 7 秒的耗时直接写在可见测试里。模型加一个 id 索引就收工，11 步——**失败信号可见时，模型顺着信号修，性能题等于给了答案**。
- 0020 把线索藏进题面（可见测试全绿，性能只在隐藏测试里）。模型自己写了 `bench_tmp.py` 造基准再优化，19 步、41k 输入，是全套里最贵的一题。
- 0016 第一轮可见绿、隐藏红：只把 `balances()` 改成实时，没做原子性。补了「转账失败时任何一侧都不能变」之后 15 步通过。
- 0005 隐藏测试要求裸 `\r`，但 TASK.md 只写了 `\r\n`——这是**测试超纲**，不是模型的问题。补 spec 后通过。

这两次是隐藏测试唯一抓到的问题，且都不是能力问题，而是题面与测试不一致。

## 7. 结论与局限

- 这套题现在测的是**成本曲线**，不是能力边界：20/20、失败分类为空。
- 难度必须放在「没写也得做对」的不变量上（原子性、兼容旧数据、性能预算），而不是放在「写得更晦涩」上。
- 样本只有单次全量、单一模型，没有重复实验，不能谈统计显著性。
- 任务规模小，最长 15 步；长程任务（几十步、跨多文件重构）没有被覆盖。

下一步：长程任务、模糊需求、旧数据兼容，以及把失败分类器跑出样本。

## 8. 复现

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m evals.run_suite --limit 3   # 先跑 3 题
.\.venv\Scripts\python.exe -m evals.run_suite             # 全量 20 题
```

需要 `DEEPSEEK_API_KEY`（或 Windows 凭据管理器里的同名凭据）。单轮全量约 3 万输入 token，成本在 $0.05 以内。
