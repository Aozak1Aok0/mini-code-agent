# W3 难度升级：隐式需求任务（2026-11-05）

## 为什么要加

上一轮 12 个任务 12/12，失败分类器一个样本都没拿到。问题不是 harness，是题目：
现状这批任务的错误都在「测试直接指出来」的位置，agent 读 traceback 就能改。

这一轮加 3 个任务，共同点是 **TASK.md 只描述现象，不给文件名**，且错误跨文件、需要先复现：

| 任务 | TASK.md 里写的现象 | 真正的坑 |
|---|---|---|
| 0013_bugfix_report | 删一条后刷新列表直接 `KeyError`，只删不刷新正常 | `storage.delete()` 只删 `_rows`，没删 `_order` |
| 0014_bugfix_export | 第二次导出混着上一次的行，重启进程就正常 | `exporter.py` 的模块级 `_buffer` 从不清空 |
| 0015_bugfix_cache | 同一函数换参数还是老结果，重启就正常 | 缓存键只用了函数名，忽略了参数 |

## 结果

全量 15 题：**15/15**，平均 7.5 步，8,617 in / 468 out token，P50 10.2s，约 $0.043/轮。

新增的 3 题单独看：

| 指标 | 3 个新任务 | 全量 15 题 |
|---|---|---|
| 解决率 | 3/3 | 15/15 |
| 平均步数 | 9.0 | 7.5 |
| token / 任务 | 10,454 in / 531 out | 8,617 in / 468 out |
| 延迟 P50 | 12.4s | 10.2s |

## 结论

1. **难度确实让成本上升，但没产生失败。** 步数 +20%、输入 token +21%，仍然全绿。
   这三个坑都需要先读代码、再看测试、最后定位，agent 都走完了。
2. **指标依然不敏感。** 15/15 意味着这套任务现在衡量的是「循环稳定、工具可用」，
   不是「模型能力上限」。作为评测，它的信息量在下降。
3. **延迟不要把两轮直接比。** P50 从 6.9s 到 10.2s 有相当一部分是 API 侧波动
   （两轮跑在不同时段），步数和 token 才是可靠信号。
4. **失败分类仍无样本。** `no_edit` / `wrong_fix` / `no_test_run` / `loop` 六类都还没被触发过，
   这套分类逻辑目前只有定义，没有验证。

## 下一步（W3 后半）

要让指标重新有区分度，三条路选一条：

- **加规模**：单个任务 300+ 行、6+ 文件，错误点离症状 3 层调用以上；
- **加约束**：公共 API 不得变、只允许最小改动、必须保持另一组回归测试全绿；
- **换判分**：隐藏测试（agent 看不到验收用例）+ 回归集，而不是「仓库里的测试全绿」。

前两条改题目，第三条改评测设计；第三条最容易做出区分度，也最接近真实工程里的验收方式。

## 隐藏测试（W3 后半）

上一节第 3 条路：把「可见测试全绿」换成「可见 + 隐藏都绿」。7 个任务加了
`tasks/<id>/hidden/test_hidden.py`，复制 workspace 时排除 `hidden/`，agent 跑完
可见测试后由 harness 合并再跑一遍；隐藏不过记为 `hidden_test_failed`。

### 公平原则

隐藏测试只能测 TASK.md 能推出的行为。第一轮 0005 就踩了这条：hidden 测了裸 `\r`
换行，而 TASK.md 只写了 `\r\n`，agent 按 spec 修完仍然失败——这不是模型的问题，
是题目的问题。处理方式是补 TASK.md 而不是删测试：

> 换行符要同时支持 `\n`、`\r\n` 和单独的 `\r`（老式 Mac 换行）。

### 结果

| 轮次 | 解决率 | 说明 |
|---|---|---|
| 首轮 | 14/15 | 0005 隐藏测试失败（spec 未覆盖裸 `\r`） |
| 补 spec 后 | 15/15 | 0005 通过：8 步、10,546 in / 409 out |

全量 15 题（runs/suite-w3-hidden-final）：平均 7.6 步、8,651 in / 472 out、P50 7.6s，
各类别 8/8、4/4、3/3。

### 结论

1. **机制可用但还没证明有区分度。** 7 个任务的参考修复全部通过隐藏测试，判分能把
   「可见绿」和「隐藏绿」分开；但这一轮没有抓到真正的能力差异。
2. **首轮唯一的失败是 spec 缺口，不是模型失败。** 这条比 15/15 更值得写进报告：
   隐藏测试如果超出任务描述，测的就是「猜作者意图」。
3. **覆盖不全。** 只有 7/15 有 hidden，其余 8 题仍是可见测试即验收。
4. **下一轮要区分度，只能动题目规模或约束**（300 行 / 6 文件 / 公共 API 不变 /
   最小改动），或者给全部 15 题补 hidden 之后再换更难的题。

### 复现

```powershell
.\.venv\Scripts\python.exe -m evals.run_suite                      # 全量，含隐藏测试
.\.venv\Scripts\python.exe -m evals.run_suite --tasks "tasks/0005_*"
```

## 扩到 17 题 + 全量隐藏测试（A+B，2026-11-05）

用户选了「A 加大任务 + B 补全隐藏测试」，两件一起做：

- 新增 0016_bugfix_transfer（6 个模块：errors / models / store / ledger / service / api）与
  0017_bugfix_idem（pricing / keyer / orders / service / api），都是「现象清楚、根因跨模块」的形态；
- 17 个任务全部配上 `hidden/test_hidden.py`，覆盖 100%。

### 结果

| 分组 | n | 解决率 | 平均步数 | 输入 token | 输出 token | P50 |
|---|---|---|---|---|---|---|
| 15 个小题 | 15 | 15/15 | 7.5 | 8,428 | 463 | 7.6s |
| 2 个大题 | 2 | 2/2 | 13.5 | 21,295 | 1,066 | 12.1s |
| 全部 | 17 | 17/17 | 8.2 | 9,942 | 534 | 8.2s |

大题的步数是小题的 1.8 倍、输入 token 2.5 倍，但**解决率还是 100%**。

### 0016 的一次真实失败

第一次跑 0016 时：可见测试全绿，隐藏测试红。agent 把 `Store.balances()` 改成读实时余额，
治好了「连续转账透支」，但没做原子性——转给一个不存在的账户时，源账户已经被扣款。

复查 TASK.md：只写了「余额变成负数」，没写失败路径不能只扣一边。按公平原则补了 spec
（「转账是原子的，失败时任何一侧都不能变」），重跑 15 步通过、输入 27,373 token。

这条比 17/17 更有信息量：**spec 没写的要求，agent 不会自己补**；写完它就能做到。

### 结论

1. 这套题现在测的是**成本**，不是成功率——17/17 说明难度还没到能力边界。
2. 隐藏测试的价值在「抓半吊子修复」：0016 那种只治可见症状的改法，隐藏测试一枪打掉。
3. 要拿到失败率，下一轮只能换形态：多文件重构 + 公共 API 约束、模糊需求、或者 300 行以上
   且错误点离症状 4 层调用的仓库。单纯加题目数量没用。
